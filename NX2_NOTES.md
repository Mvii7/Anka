# Eden on Switch 2 titles (branch `nx2`)

Local experiment: get Eden (Switch 1 emulator) to load a Switch 2 title's loose ExeFS and push
boot as far as it goes. Nothing here is upstreamed or pushed. Graphics (Ampere / NVN2) is out of
scope for this pass.

## Setup

- Source + build live in `C:\dev\eden` (a worktree of `eden-nx2/`, branch `nx2`). The original
  working folder path is ~180 chars, and `cl.exe` can't open its PDB from a build folder there
  (C1041), so the build moved to a short path.
- Toolchain: VS 2026 (MSVC 14.51) via `vcvars64.bat`, Ninja from VS, CMake 4.4.
- Configure:
  `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_INTERMEDIATE_DIR_STRATEGY=SHORT -DENABLE_QT=OFF -DYUZU_CMD=ON -DENABLE_WEB_SERVICE=OFF -DYUZU_ROOM=OFF -DYUZU_TESTS=OFF -DENABLE_WERROR=OFF -DENABLE_UPDATE_CHECKER=OFF`
- Build: `cmake --build build --target yuzu-cmd` -> `build/bin/eden-cli.exe`.
- Run (portable mode, `build/bin/user/` holds config/logs; no keys or firmware installed):
  `eden-cli.exe -g "<title>\exefs\main"`
- Debug helpers:
  - `EDEN_NX2_SVC_TRACE=1` logs every SVC with arguments and results.
  - `EDEN_NX2_IPC_TRACE=1` logs every dispatched CMIF command and non-zero result words. Any other
    value is a filter for request backtraces (`nx2:vi2:104,105,107`; `all` and `nx2:vi2` work but
    stall the game at each new command; see "Live vi2 reply experiments" below).
  - Switch 2 modules in backtraces: `Core::FindModules` names a module by the module path that
    follows its .text; Switch 2 modules (rtld, main, sdk) have none, so it found nothing and
    every frame was "(no module)". The NSO loader now registers each module it places with the
    process (`KProcess::RegisterLoadedModule`: base, end, name, the NSO header's .dynsym /
    .dynstr), and FindModules adds the registered modules its path scan did not find. Switch 1
    modules are found by the scan first, as before. Crash backtraces, the gdbstub module list
    and the IPC trace all use FindModules.
  - `EDEN_NX2_AUTO_STUB=1` answers every unknown command with an empty success (the
    `use_auto_stub` setting gets reset by eden-cli's config rewrite). Used for all runs below.
  - `eden-cli --filter "<log filter>"` sets the log filter for one run (e.g. `*:Info Loader:Debug`
    to get module load addresses).
  - `tools/nx2/nso_syms.py <nso> addr|got|find ...` maps module offsets to exported symbols, GOT
    slots to imports, or searches symbol names. Eden's backtrace shows "unknown" modules for some
    titles; with the `loaded module X @ addr` lines this turns frames into SDK names.
  - `tools/nx2/a64_coverage.py <a64.inc> <nso>...` lists encodings in an NSO's .text that
    dynarmic's decoder table doesn't match.
  - `tools/nx2/npdm_info.py <main.npdm>` dumps the META/ACI0 header, services and kernel caps.
  - `tools/nx2/nso_dis.py <llvm bin> <nso> <text_off> <count> <workdir>` disassembles part of an
    NSO's .text (clang + llvm-objdump from VS 2022's LLVM).
  - Under cdb, stop only on second-chance AVs (`sxd -c2 "..." av`): dynarmic fastmem uses
    first-chance access violations.

## Titles

All titles share the same `main.npdm` layout: 64-bit, 39-bit address space, ThreadInfo cores
0..5 (core mask 0x3f), priorities 28..59, KernelVersion cap 9.1, SVCs 0x01-0x36 plus 0x80,
Switch 2 ACID layout.

All four are **Switch 2 builds**: none is a plain Switch 1 sanity check. Instruction counts that
stock dynarmic did not decode (`a64_coverage.py` against the unpatched `a64.inc`):

| Title (ExeFS) | Program id | RETAA/B | LDAPR | LSE atomics | CAS | SWP | other |
|---|---|---|---|---|---|---|---|
| first `exefs` | 0400C3F00006E000 | 114,767 | 37,560 | 24,718 | 6,640 | 2,470 | CASP 6, XPAC 7, PAC 2, STG 1 |
| second `exefs` and `updates/exefs` | 0400A3A01EE4C000 | 12 (rtld only) | - | - | - | - | main/sdk/subsdk0 don't decompress |
| third `exefs` (update `updates/65536` ~same) | 04005B902517C000 | 134,287 | 37,052 | 160,741 | 19,987 | 1,623 | XPAC 3, PAC 2, STG 1 |
| fourth `exefs` (update `updates/65536` ~same) | 0400380020056000 | 134,911 | 100,520 | 32,110 | 8,667 | 3,733 | PACGA 58, PAC 7, CASP 6, XPAC 3, STG 1 |

With the patched decoder, games 1/3/4 only leave ~60-110 rare SIMD encodings in `sdk` undecoded
(e.g. `5f119f9c`, `4ea05c42`, `0f413044`, FP16/v8.2 forms).

### Live vi2 reply experiments (IPC trace + reply table)

Bananza sends nx2:vi2 104, 105 and 107 every frame and 261, 265, 267, 271 (each after a 31
GetVsyncEvent with the same index) and 351 once at setup, all with the display name "default".
104/105 got an empty success, the rest the auto stub's. On the console the game runs 40-60 fps in
handheld VRR without slowing down, so these are likely its VRR / HDR display queries
(`nn::vi::QueryDisplayVrrSupported`, `SetDisplayVrrCapability`, `SetLayerExtendedSwapInterval`,
`QueryDisplayHdrStatus`... are imported).

1. Which SDK function sends a command: `EDEN_NX2_IPC_TRACE=nx2:vi2:104,105,107,261,265,267,271,351`.
   The log gets, once per new request,
   `nx2 ipc trace N/400: nx2:vi2 104 [tipc] "<handler>", 2 data words: 0x61666564 0x746c7561; thread 0x.. "<name>"`
   and frame lines `  #i <module> +0x<offset> <raw symbol>+0x<into> = <demangled>`, e.g.
   `  #3 sdk +0x... _ZN2nn2vi6detail14DefaultDisplay17QueryVrrSupported...+0x.. = nn::vi::detail::DefaultDisplay::QueryVrrSupported(...)`
   (sdk's names come from its .dynsym; main has few). Frames 0-1 are
   the SVC stub and the IPC layer; the first `nn::vi::...` frame names the call, its mangled name
   the parameter types (and so the reply's shape). Keep the command list: with a bare `nx2:vi2`
   each command is traced once (229, every present, too), and each trace holds core 3's IPC for
   up to 20 ms. The sender waits in the kernel while a service
   thread handles the request; the trace reads the registers the scheduler saved when it switched
   the sender out (it waits up to 20 ms for that; "registers may be stale" if it never happened).
2. Answer it: `EDEN_NX2_VI2_REPLY_FILE=<path>`, one command a line, words decimal or 0x hex, `#`
   comments, an empty list a success without data words:

       # VRR experiment
       104: 1
       105:
       107: 0x3c

   (inline: `EDEN_NX2_VI2_REPLY=104:1;105:;107:0x3c`). The table covers 104, 105, 107, 261, 265,
   267, 271, 351 and any other command without a handler of its own that is in the table when the
   vi2 session opens; commands with handlers (1, 3, 31, 229...) are never replaced ("has a handler
   of its own, not replaced"). A command not in the table keeps its old reply (an empty success).
   The setup commands (261-351) are sent once, when the session opens: put them in the file
   before starting the game; changing them later does nothing until the next boot. The per-frame
   ones (104, 105, 107) can be edited while the game runs: the file is checked at most once a
   second (on those calls) and re-read when its time or size changes.
   Log: `nx2:vi2 reply table v3: 104=[0x1] 105=[] 107=[0x3c]` on each new table,
   `nx2:vi2 reply v3: 104 -> [0x1]` on each command's first call and its first call after a change
   (`-> empty success (not in the table)` for one without a reply), `nx2:vi2 reply table: <why>;
   keeping v2` when the file can't be read or parsed (the previous table stays; a UTF-16 file:
   "UTF-16 file, save it as UTF-8"), `nx2:vi2 reply table v3: 300 not answered: commands get a
   table handler when a vi2 session opens (restart the game)` (or `...: a handler of its own`)
   when a new table lists commands the open sessions do not answer from it, and with
   `EDEN_NX2_PRESENT_DIAG=1` ", reply v3" at the end of the per-second line.
   Reply layout (TipcReplyWords, checked by reading ResponseBuilder, not by a test): for n words
   the header's data size is 1 + n, word 2 the result, words 3.. the reply, 3 + n words written.
   A reply of the wrong length can break the game: the SDK copies as many words as the command's
   reply has and reads the rest from stale memory, or rejects the reply (an abort). Start from
   the size the trace's mangled name implies.
   104 is GetHdrStatus(u64 display name) (moceure/eden-nx2-android 01226f4e94): result, u64
   output format (1 = SDR), u32 0; a display name other than "default" gets VI error 7. The
   table writes that reply as it is, no code needed (same ResponseBuilder size, 5, and the same
   four words): `104: 1 0 0` (inline `EDEN_NX2_VI2_REPLY=104:1,0,0`). The empty success before
   left the format to stale reply words, from which a game may set up HDR output (washed-out
   colours, a white halo: worth a try against H1). Bananza only asks for "default", so the
   error reply is not missed. The "# VRR experiment" example's `104: 1` above is the wrong
   size for it (one word of three).
   Since then every command below 4096 without a handler answers from the table, so one the
   game has not sent before can be answered once a line for it is added (an empty success as
   before until then).

## up25: picks from 2.5.0 (perf/up25)

Cherry-picked from PokeDinner 2.5.0 (216b5034c) onto perf/tam faddee043; no full merge.

- HMMA is emulated by default (f5e1b2bcd, 55c9b8745: f32 accumulators in R240-R243, F2F after
  every eight products), which replaces row 64's opt-in. `EDEN_NX2_TENSOR=off` (or `0`) rejects the
  program as the old default did ("native matrix multiply (EDEN_NX2_TENSOR=off)"), so
  KeplerCompute's upscale stand-in (`EDEN_NX2_UPSCALE_*`) runs again; `=stub` makes D = C.
- R240-R245 also hold UR22-UR27 (programs with a uniform bank) or ordinary registers (programs
  without one, which may use up to R245). A program that both emulates an HMMA and maps UR22-UR27
  or names R240-R245 is rejected with "native matrix multiply scratch overlaps R240-R245" and gets
  the stand-in. R237-R239 count only as the base of an unaligned register list (texture and
  surface ops, LDSM, ALD / AST); aligned pairs and quads end at R239. `EDEN_NX2_TENSOR=unguarded`
  emulates it anyway (upstream's behaviour), for A/B.
- Once an HMMA is emulated, any later rejection of the program is reported as "native matrix
  multiply program: <reason>", and a program with an emulated HMMA whose compute pipeline fails to
  build throws "Native matrix multiply program has no compute pipeline" (Vulkan): both keep the
  upscale stand-in the old first-HMMA rejection gave. Not with `stub` or `unguarded`.
- FP16 TEX results pack c0 in the low half (ee247a0b6).
- Pipeline cache versions 1019 (Vulkan) and 1016 (OpenGL): the disk cache holds lowered code. The
  first session rebuilds every pipeline. 2.5.0's 19 is a different file layout.
- The 3D register-write history records only with `EDEN_NX2_3D_HISTORY` in release builds
  (1a346fb3b); RecordWrite is gated itself, so both the K1 (BackLoop) and staged (RunStagedBack)
  consumers skip it. Unlike upstream, `EDEN_NX2_3D_HISTORY=0` leaves it off (a leading '0' is off,
  as for our other switches). Native macro parameters run without a second FIFO copy (665938d0b).
- Invalid sampler / image view index logs are LOG_TRACE (idea from Djihads PR #374).
- Not taken: b2430b4d9 (needs vk_rasterizer.cpp), ddbd076cf (only for >16 removals at once).
